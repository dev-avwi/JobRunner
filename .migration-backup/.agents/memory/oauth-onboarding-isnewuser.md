---
name: OAuth onboarding routing via isNewUser
description: Why mobile Google/Apple OAuth handlers must route brand-new users by the server isNewUser flag, not onboardingCompleted
---

Mobile OAuth (Google + Apple) handlers must route brand-new users to the onboarding wizard based on the server-provided `isNewUser` flag, NOT on `businessSettings.onboardingCompleted`.

**Why:** All OAuth handlers historically called `resolvePostAuthRedirect()`, which decides solely on `onboardingCompleted`. The server's `createGoogleUser`/`createAppleUser` create NO business_settings and NO team membership, so GET /api/business-settings auto-heals a missing row to `onboardingCompleted = isStaffOnOtherTeam`. A genuinely new account that gets misclassified as staff (e.g. `/api/team/my-role` resolves an accepted membership) ends up `onboardingCompleted=true` and silently skips the wizard, landing on the dashboard. The auto-heal read-back is also racy.

**How to apply:** Server already emits `isNewUser` — Google via deep-link query param (`jobrunner://?auth=google_success&token=...&isNewUser=...`, server/googleAuth.ts), Apple via JSON response field (server/routes.ts /api/auth/apple). In the mobile handlers (`mobile/app/(auth)/login.tsx` + `register.tsx`: Google deep-link useEffect, handleGoogleSignIn token + no-token branches, Apple handler), when `isNewUser` is true → `router.replace('/(onboarding)/setup')`; else fall back to `resolvePostAuthRedirect()`. Safe because `isNewUser=true` only when a fresh users row was created (existing/linked accounts, including genuine invited workers, return `isNewUser=false`).

**CONFIRMED real-world root cause (prod DB inspection):** the user kept retesting on a device that hits the live site (mobile `PROD_FALLBACK_API_URL = https://jobrunner.com.au`, used whenever `!__DEV__`), NOT the dev workspace — the dev DB had ZERO google_id/apple_id users. The live site runs OLDER server code whose auto-heal misclassified brand-new OAuth signups as workers: prod accounts created with `business_settings.business_name = "Worker Profile"`, `onboarding_completed = true`, and ZERO team memberships → they skip the wizard and land on the dashboard with a "Team member" badge. The current repo's auto-heal already fixes this (0 memberships → `onboarding_completed=false`, name `<FirstName>'s Business`). So the fix is a PUBLISH, not more code. Caveat: already-created accounts stay `onboarding_completed=true` in prod even after publishing — to retest, use a fresh email or reset the affected rows (prod write needs user consent; my tools query prod read-only). Note `business_settings` has NO `trade_type` column (it's on `users`), so the L8325 `hasBusinessSetup = businessName && tradeType` second-heal can't fire for a fresh owner — good, it stays false.

**SECOND root cause — default businessName trips stale-client auto-complete (prod logs 08:32:55-57):** even after the auto-heal correctly creates a new OWNER with `onboarding_completed=false`, the mobile client one second later fires `POST /api/onboarding/complete` on its own and lands the user on the dashboard. Cause: the auto-heal pre-filled `businessName="<FirstName>'s Business"`; the mobile build treats "settings.businessName is present" as "business setup done" (`hasBusinessSetup`) and auto-completes the wizard. So the cosmetic default name is what skips onboarding — for ANY client build with that auto-complete (the user's stale Metro build AND the published mobile build). Fix is server-side and client-version-independent: in the GET /api/business-settings auto-heal, set new-owner `businessName: ''` (empty) — workers/subs still get WORKER_PROFILE_PLACEHOLDER_NAME + completed=true. Empty businessName → `hasBusinessSetup=false` on every client → wizard's business step, no auto-complete; and the second server heal (`businessName && tradeType`) also can't fire. `business_settings.business_name` is `NOT NULL`, so use `''` not null. **Centralization gap:** other create-fallback paths must NOT pre-fill an owner default name either — `PUT /api/settings/sms-branding` was also fixed from `'My Business'` to `''`. Any NEW createBusinessSettings fallback for a not-yet-onboarded owner must use `businessName: ''`.

**Related:** the two dashboard spinner cards (TimeTrackingWidget `/api/time-tracking/dashboard`, WeatherWidget `/api/weather`) are NOT a perpetual-spinner bug — both have `finally{setIsLoading(false)}`, the 12s refresh never re-sets isLoading=true, and the api client aborts after 15s. Stuck cards = slow/stale backend latency (PROD_FALLBACK), not a frontend defect.
