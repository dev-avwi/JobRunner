---
name: Owner misclassified as non-owner (self team-membership + dup settings)
description: Why an owner intermittently gets 403 on owner-only routes and how owner detection must stay deterministic.
---
A business owner can be wrongly resolved as a NON-owner (isOwner=false) when ALL of:
- users.active_business_id is null, AND
- a self team_members row exists (member_id === business_owner_id, accepted), AND
- getBusinessSettings returns an empty/placeholder-name row.

getUserContext (server/permissions.ts): when active_business_id is null it reads getBusinessSettings; if businessName is empty/"Worker Profile" it falls back to getTeamMembershipByMemberId, finds the self-membership, and marks isOwner=false → ownerOnly() 403s every owner-only route (saves, team, billing). Because getBusinessSettings cached for 60s and used to do .limit(1) with NO order, with duplicate business_settings rows the chosen row (and thus owner status) was NONDETERMINISTIC → intermittent "saves/team functions break".

**Rule 1:** getBusinessSettings MUST order deterministically — prefer a real businessName (not '' and not 'Worker Profile') via CASE, then updatedAt/createdAt desc — never bare limit(1).
**Rule 2:** In getUserContext, a membership whose businessOwnerId === userId is a SELF row; treat that user as the owner (clear teamMembership), never as their own employee.
**Why:** prod owners accumulated duplicate business_settings (legacy onboarding PATCH-then-POST) + a self team_members row; this combo silently locked them out.
**How to apply:** any new owner/permission resolution path must not rely on an unordered settings lookup, and must guard self-memberships. Duplicate business_settings rows still exist in prod data (read-only) — dedupe is a separate user-gated cleanup; a unique constraint on business_settings.user_id would prevent recurrence.

**Rule 4 (owner shows "Team member" but server is already correct = STALE MOBILE CACHE, not a server bug):** if an owner reports the wrong badge yet prod data shows the account owns a business with ZERO team_members rows AND /api/auth/me + /api/team/my-role return isOwner:true, the bug is the device's cached `roleInfo`. The mobile store (store.ts) only refreshes role on a full cold-start online checkAuth; a transient network blip on cold-start (or the init guard skipping re-check, or a stale Metro JS build) leaves a previously-cached worker `roleInfo` showing forever. **Why:** the "Worker Profile" placeholder accounts were once real workers, so their device cached a worker role; after the membership was removed the cache never self-corrected. **How to apply:** treat /api/auth/me `isOwner` as authoritative and overwrite a stale worker `roleInfo` to OWNER in BOTH checkAuth (online-success, before fetchRoleInfo) and refreshUser (focus/pull-to-refresh self-heal). Only ever FORCE the owner case, never the worker case (forcing worker would mislabel real owners). Always verify the actual account in the PROD replica first — these accounts live only in production, not the dev DB.

**Rule 5 (the mobile role badge is driven ONLY by store.roleInfo.roleName from /api/team/my-role; self-heal must refresh it, and fetchRoleInfo must NOT escalate to owner on failure).** index.tsx badge = isSubcontractorUser(roleName lowercased==='subcontractor'/'sub_contractor') ? Subcontractor : owner ? Owner : roleName!=='STAFF' ? roleName : 'Team member'. /api/auth/me's isOwner only fixes the OWNER case; subcontractor/worker badges depend on my-role's roleName, so the focus/pull-to-refresh self-heal in refreshUser must call fetchRoleInfo (not just the owner override) to recover ANY stale role. **FOOTGUN:** fetchRoleInfo historically defaulted to OWNER (roleName 'OWNER', isOwner:true, perms ['*']) on BOTH empty-response and catch branches. Once refreshUser calls it on every focus, that fallback fires on transient my-role blips and gets persisted via cacheAuthData → a real subcontractor/worker silently shown/cached as owner (client-side role escalation). **Fix/rule:** only apply the owner default when `!get().roleInfo` (true cold-start unknown); on any failure WITH a prior role, preserve the existing role and don't touch setSubcontractorMode. Server subcontractor role is guaranteed named "Subcontractor" (upgrade flow creates it if missing); membership creation is gated by owner tier/seat limits, so a "subcontractor" with no accepted team_members row hits the owner-fallback path — that's a provisioning issue, not a badge bug.

**Rule 3 (the guard is NOT only in getUserContext):** several endpoints resolve role DIRECTLY via storage.getTeamMembershipByMemberId(userId) and were missing the self-guard, so a self-membership owner gets a worker role / isOwner:false. Confirmed-fixed surfaces: GET /api/team/my-role and its aggregate mirror `teamMyRole` (these drive the mobile dashboard "Owner" badge + worker-only MY STATUS pills via store.fetchRoleInfo). Still UNGUARDED (known follow-ups, flagged by review): GET /api/profile/me, getTeamChatContext helper, and the number-porting/manager-gated routes that read membership.role directly. Best fix long-term: a shared "membership lookup with self normalization" helper (or just call getUserContext) instead of repeating the raw getTeamMembershipByMemberId + role branch.
