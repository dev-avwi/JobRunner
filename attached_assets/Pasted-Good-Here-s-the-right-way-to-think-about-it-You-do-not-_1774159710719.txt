⸻

JobRunner Production Readiness Checklist

1. Data isolation

This is one of the most important things in your whole app.

Ask yourself:
	•	Can one business ever see another business’s:
	•	jobs
	•	clients
	•	invoices
	•	team
	•	messages
	•	files
	•	AI call records
	•	Does every important query include the business/account scope?
	•	If a worker manually changes a URL or request, can they access something they shouldn’t?

Green flag

Every major record is tied to a business/account ID.

Red flag

You’re relying mostly on frontend hiding, instead of backend checks.

⸻

2. Auth and permissions

You need strong role logic.

Check:
	•	owner can do everything
	•	admin can do only what admins should
	•	workers can only access their allowed views
	•	clients cannot access internal business data
	•	support/demo/admin tools are protected

Ask:

If someone is logged in as a worker, what’s the worst thing they can wrongly access?

If the answer is “a lot,” fix that.

⸻

3. Database structure

This is the skeleton of the app.

You should clearly know the relationships between:
	•	Business
	•	User
	•	Team Member
	•	Client
	•	Job
	•	Job Note
	•	Invoice
	•	Quote
	•	Time Log
	•	AI Call / Lead
	•	Chat Thread
	•	File Upload
	•	Payment / Billing record

Ask:

Can you explain the whole data model on paper?

If not, you need to slow down and map it.

Red flags
	•	duplicated client records everywhere
	•	jobs not clearly linked to clients/businesses
	•	chat threads not scoped cleanly
	•	weird “temporary” tables you no longer understand

⸻

4. Error handling

Production apps don’t just need to work when everything goes right.
They need to fail safely.

Check:
	•	what happens if Twilio fails?
	•	what happens if AI webhook fails?
	•	what happens if Stripe webhook arrives twice?
	•	what happens if SendGrid fails?
	•	what happens if file upload fails?
	•	what happens if push notification fails?

Good pattern
	•	log the error
	•	keep the record
	•	show a safe message
	•	retry where needed
	•	never silently fail

Bad pattern

“Something broke and nobody knows why.”

⸻

5. Logging and monitoring

If real users use it, you need visibility.

You should have:
	•	app error tracking
	•	server logs
	•	webhook logs
	•	failed job logs
	•	failed SMS/email logs
	•	billing event logs

At minimum

Use:
	•	error monitoring
	•	uptime monitoring
	•	logs for important flows

Critical flows to log
	•	login/signup
	•	job creation
	•	AI receptionist lead creation
	•	owner approval
	•	SMS send
	•	invoice send
	•	payment events
	•	file upload

If these fail, you need to know.

⸻

6. Background jobs / async work

This matters a lot for scaling.

Things that should ideally not block the main user request:
	•	sending SMS
	•	sending email
	•	processing AI transcripts
	•	generating PDFs
	•	uploading files
	•	syncing notifications

Ask:

Is too much happening in one request?

If a single action is:
	•	create job
	•	generate invoice
	•	send email
	•	send SMS
	•	open chat
	•	save transcript

all at once in one fragile path, that can get messy fast.

⸻

7. Performance

You do not need crazy infrastructure yet.
But you do need to think properly.

Check:
	•	are dashboards loading too much data at once?
	•	are job lists paginated?
	•	are chat threads paginated?
	•	are image/file heavy pages optimised?
	•	are you making too many duplicate API calls?
	•	are large queries filtered by business/date/status?

Red flags
	•	huge “load everything” queries
	•	dashboard tries to fetch the whole universe
	•	repeated data fetching on every screen render
	•	no pagination

⸻

8. File and media handling

JobRunner likely has:
	•	photos
	•	invoices
	•	quotes
	•	SWMS docs
	•	attachments
	•	maybe call recordings later

Check:
	•	where are files stored?
	•	are they separate from app code?
	•	are links secure?
	•	can one business access another business’s files?
	•	do uploads have size/type limits?

Red flags
	•	files stored in messy local folders
	•	insecure public URLs
	•	no cleanup strategy
	•	no per-business access control

⸻

9. Billing safety

Because you already have Stripe, this is important.

Check:
	•	can one event create duplicate subscriptions?
	•	do seat changes update billing properly?
	•	what happens if payment fails?
	•	what happens if a user cancels?
	•	do webhooks verify correctly?
	•	are plan limits enforced in app logic?

Important

Never trust only the frontend for plan access.

Backend should know:
	•	current plan
	•	seat count
	•	active subscription state
	•	trial / expired / cancelled status

⸻

10. AI receptionist safety

Since this is your next big thing, give it its own checklist.

Check:
	•	call data always tied to correct business number
	•	incoming caller number handled safely
	•	client lookup is business-scoped
	•	no duplicate jobs from same webhook
	•	transcripts stored correctly
	•	no AI promise of fixed times/prices
	•	emergency paths handled clearly
	•	approval required before strong customer commitment

Most important

The AI should collect and pass info, not behave like an overconfident employee making legal promises.

⸻

11. Backups

This is boring until it matters.

Check:
	•	is your database backed up automatically?
	•	can you restore it?
	•	how often are backups made?
	•	are important files backed up too?

Ask:

If your database broke tonight, what would you actually do tomorrow?

If the answer is “panic,” improve backups.

⸻

12. Deployment safety

You want production to feel controlled.

Check:
	•	is code versioned in GitHub?
	•	can you roll back to previous version?
	•	do you test before production deploy?
	•	do env variables/secrets stay out of code?
	•	do you have separate dev and prod setups?

Red flags
	•	editing production blindly
	•	no rollback
	•	secrets hardcoded
	•	dev and prod mixed together

⸻

13. Security basics

You do not need military-grade security yet.
But you need solid basics.

Check:
	•	secrets in env vars, not code
	•	strong auth/session handling
	•	backend permission checks
	•	webhook signature verification
	•	rate limiting where needed
	•	file upload validation
	•	no exposed admin endpoints
	•	no debug tools left open in production

⸻

14. UX reliability

Production quality is also about trust.

Check:
	•	do destructive actions have confirmation?
	•	are loading states clear?
	•	are empty states clear?
	•	can users recover from mistakes?
	•	is there feedback after actions?
	•	does every important action feel stable?

A reliable-feeling app wins even before “big scale” arrives.

Production scorecard for yourself

Rate each section from 1 to 5:
	•	Data isolation
	•	Auth/permissions
	•	Database structure
	•	Error handling
	•	Logging/monitoring
	•	Background jobs
	•	Performance

	•	Deployment safety
	•	Security basics
	•	UX reliability

Meaning

	•	3 = okay but fragile
	•	5 = strong and production-ready

Anything at 1 or 2 is where you should focus first.

Your immediate production priorities for JobRunner

If I were you, I’d focus on these first:

Priority 1

Business data isolation
Because if that breaks, it’s serious.

Priority 2

Error monitoring + logging
Because once pilot users start, you need visibility.

Priority 3

Billing and auth safety
Because trust matters.

Priority 4

AI receptionist flow reliability
Because this is your biggest differentiator.

Priority 5

Backups + rollback
Because real businesses hate data loss more than almost anything.

What “good for production” actually means for you right now

Not:
	•	5 nines uptime
	•	massive Kubernetes cluster
	•	giant engineering team

It means:

a small number of real businesses can rely on JobRunner without it feeling sketchy

That’s the real milestone.

⸻

My honest founder advice

Don’t obsess over:

“Can it handle 10,000 users today?”

Obsess over:

“Would 5 real tradie businesses trust this next month?”

That is the right production standard for your stage.

Once you pass that, you improve toward:
	•	20 users
	•	50 users
	•	100 users

That’s how real products scale.
