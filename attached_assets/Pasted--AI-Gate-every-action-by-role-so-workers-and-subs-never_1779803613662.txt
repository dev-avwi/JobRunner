#183 - RBAC Proactive Gating Sweep
What & Why
Today, workers, subcontractors, managers and office admins can see buttons, menu items, FABs, quick-create options and even open screens for actions they don't actually have permission to perform. The block happens only at the final API call, which feels broken and unprofessional. We need every entry point — navigation, dashboards, lists, dropdowns, FABs, inline "create" buttons inside forms — to be gated up-front from the same permission source the backend uses, so the user either doesn't see the action at all, or sees a clear, premium "locked by your team owner" affordance instead of a dead-end error.

The goal is consistent, premium permission UX across web and mobile that makes the subcontractor + multi-role workspace actually feel solid.

Done looks like
For every role (Owner, Manager, Office Admin, Worker, Subcontractor):
Sidebar / bottom-nav only lists pages the role can actually use.
Dashboard quick-create sheet (the screenshot: New Job / New Quote / New Invoice / New Client / AI Assistant / Collect Payment) only shows actions the role is allowed to perform. A worker never sees "New Job" or "New Client" there.
Floating Action Button on Jobs / Quotes / Invoices / Clients / Documents pages is hidden (or its items filtered) when the role can't create that entity.
Row-level action menus (Edit, Delete, Duplicate, Invoice, Schedule, Start, Complete, Restore, Convert to Invoice, Send, Mark Paid, etc.) only render items the user can actually execute on that record.
Inline "+ New Client" / "+ New Item" buttons inside Quote / Invoice / Job forms are hidden when the user lacks the corresponding create permission.
Detail screens (Job, Quote, Invoice, Client) don't show edit / status-change / payment / send / delete controls the role can't use.
Attempting to deep-link to a forbidden route (typed URL, old notification, magic link) lands on a clean "You don't have access to this — ask your team owner" screen, not a blank page or a silent redirect.
A single shared helper (can(action, record?)) is used by every gating decision on both web and mobile, sourced from the same permission map the backend enforces. No more ad-hoc role === 'worker' string checks scattered through components.
Where a user genuinely needs the action but their role blocks it, the UI shows a subtle lock affordance with a one-line explanation ("Only the team owner can do this") instead of just hiding silently in places where hiding would be confusing (e.g. on a record the user owns or is assigned to).
Backend permission checks remain the source of truth and are unchanged in strictness — UI gating is additive, never a replacement.
The matrix of who-can-do-what is captured in one place (doc + code constant) so future screens stay consistent.
Out of scope
Adding new permissions or new roles. We're gating the existing permission set, not redesigning it.
Changing backend permission enforcement (already correct).
Per-record fine-grained sharing rules (e.g. "this specific job is shared with this specific sub"). Only role + existing assignment rules.
Redesigning the dashboards themselves — only the action affordances on them.
Mobile native modules / build config.
Steps
Permission matrix + shared can() helper. Produce a single authoritative matrix (entity × action × role) that mirrors what the backend already enforces, and expose it through one can(action, record?) helper for web and one for mobile. Replace ad-hoc role string checks with this helper as each surface is touched in the steps below.

Navigation + route guards. Audit web sidebar, mobile bottom nav, and the route guard / protected-route components so forbidden routes are filtered from nav AND deep-links land on a proper "no access" screen instead of erroring or silently redirecting.

Dashboards + Quick Create. Gate the dashboard Quick Create sheet (New Job, New Quote, New Invoice, New Client, AI Assistant, Collect Payment) and all dashboard action tiles / shortcut buttons per role on both Owner/Manager and Worker/Tradie dashboards, web and mobile.

Floating Action Buttons + list-level create. Make every FAB and "+ New X" header button on Jobs, Quotes, Invoices, Clients, Documents, Catalog, Team, SWMS, etc. consult can() and hide entire FAB when no items remain. Cover both web and mobile.

Row action menus on lists. Sweep every list dropdown (Jobs, Quotes, Invoices, Clients, Documents, Catalog, Team, Timesheets, etc.) so each menu item — Edit, Delete, Duplicate, Convert, Schedule, Start, Complete, Restore, Send, Mark Paid, Issue Refund, Void, Share, Download, etc. — is conditionally rendered through can().

Detail / editor screens. Sweep Job, Quote, Invoice, Client, SWMS, Document, Catalog detail and edit screens on web and mobile to hide edit, status-change, payment, send, sign, lock/unlock, delete and inline "+ New Client / + New Item" controls the role can't use.

Locked affordance + empty states. Where simply hiding is confusing (e.g. a worker viewing their own assigned job, or a sub viewing a shared quote), show a subtle lock icon + tooltip / sheet explaining who can do it, instead of a dead button. Update empty states ("No jobs yet") so they don't suggest creating one to roles that can't create.

Cross-role smoke pass. For each role (Owner, Manager, Office Admin, Worker, Subcontractor) walk the full app on web and mobile and confirm no surfaced action leads to a permission-denied error. Capture screenshots into the report.

Regression guard. Add a lightweight test / lint check that asserts every API mutation route has a corresponding can() entry, so a new create/edit/delete endpoint can't ship without UI gating data.
