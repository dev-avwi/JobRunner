<div class="section">
  <div class="chapter-label">04 — Pre-solved problems</div>
  <h2>Every problem identified before building</h2>
  <p class="subtitle">These are every failure mode we could think of. Solving them now costs an hour of thinking. Discovering them in production costs weeks of rework.</p>

  <div class="callout-grid">
    <div class="callout"><div class="callout-num">24</div><div class="callout-label">Problems identified</div></div>
    <div class="callout"><div class="callout-num">24</div><div class="callout-label">Solutions defined</div></div>
    <div class="callout"><div class="callout-num">0</div><div class="callout-label">Left unresolved</div></div>
    <div class="callout"><div class="callout-num">6</div><div class="callout-label">Critical priority</div></div>
  </div>

  <h3 style="margin-bottom:12px;color:var(--red)">Critical — will break the product if not solved</h3>

  <div class="problem-block">
    <div class="problem-title"><span class="tag tag-red" style="margin:0">Critical 1</span> Video sync — annotations appearing on wrong screen</div>
    <div class="problem-body">Video plays at real speed. Claude analysis takes 3-5 seconds. By the time annotation is ready the video has moved to a different screen. User sees annotation on wrong content. Feels broken and confusing.</div>
    <div class="problem-solution">Video and analysis are fully decoupled pipelines. Video pauses maximum 3 seconds on each new screen load. If analysis finishes within 3s, annotation appears live. If not, video resumes and late annotation attaches to the correct timestamp in the timeline only — never over the current live view. Late annotations pulse in the timeline to signal a new finding on a previous screen.</div>
  </div>

  <div class="problem-block">
    <div class="problem-title"><span class="tag tag-red" style="margin:0">Critical 2</span> Screenshot timing — capturing half-loaded screens</div>
    <div class="problem-body">Playwright navigates to a new page. The screenshot fires immediately. But heavy JavaScript apps take 2-4 seconds to fully render. Screenshot captures skeleton screens or empty states that aren't the real content. Claude analyses a blank screen and gives useless feedback.</div>
    <div class="problem-solution">Two-condition wait before screenshot: (1) networkidle — no network requests for 500ms, AND (2) DOM stability check — no significant DOM mutations for 300ms via MutationObserver. Both conditions must be true before screenshot fires. Maximum wait time capped at 8 seconds to prevent hanging on apps with polling requests.</div>
  </div>

  <div class="problem-block">
    <div class="problem-title"><span class="tag tag-red" style="margin:0">Critical 3</span> Single page apps not triggering navigation events</div>
    <div class="problem-body">React/Vue/Angular apps change content without a full page navigation. Playwright's waitForNavigation never fires. The crawler sits on the first screen forever thinking nothing happened. Misses 90% of the app.</div>
    <div class="problem-solution">Watch two signals simultaneously: URL hash/path changes via History API, AND significant DOM mutations (>20% of visible DOM changed) via MutationObserver. Either signal triggers a new screen discovery event. Debounce DOM mutations by 500ms to avoid firing on every animation frame.</div>
  </div>

  <div class="problem-block">
    <div class="problem-title"><span class="tag tag-red" style="margin:0">Critical 4</span> Cloudflare and bot protection blocking the crawler</div>
    <div class="problem-body">Many production apps use Cloudflare, Imperva, or other bot protection. The crawler gets served a CAPTCHA or blocked page within seconds. User thinks your product is broken. You have no control over their CDN config.</div>
    <div class="problem-solution">Use Playwright with stealth mode plugin to reduce bot detection signals. Detect block pages by checking for known CAPTCHA selectors or HTTP 403/429 responses. When detected, immediately stop the run and show a clear, helpful message: "Bot protection detected on this app. To proceed: (1) whitelist our crawler IP [IP address], or (2) use manual screenshot upload." Never let the run silently fail.</div>
  </div>

  <div class="problem-block">
    <div class="problem-title"><span class="tag tag-red" style="margin:0">Critical 5</span> S3 storage costs growing unbounded</div>
    <div class="problem-body">Every scan produces hundreds of PNG screenshots plus two MP4 files. Without expiry policies this grows without limit. Storage costs compound fast across many users.</div>
    <div class="problem-solution">Free tier: S3 lifecycle rule auto-deletes all assets after 30 days. Paid tier: 1-year retention. Enterprise: custom retention. Shareable links check if assets still exist before serving — if expired, show a clear "This report has expired. Re-run the scan to generate a new one." message. Store only the JSON analysis results permanently — screenshots and videos are regeneratable.</div>
  </div>

  <div class="problem-block">
    <div class="problem-title"><span class="tag tag-red" style="margin:0">Critical 6</span> Claude API rate limits during parallel analysis</div>
    <div class="problem-body">Running six analysis passes across 20 screens simultaneously means potentially 120 Claude API calls in a few minutes. Hitting rate limits causes analysis jobs to fail silently or return errors that get stored as results.</div>
    <div class="problem-solution">Implement exponential backoff with jitter on all Claude API calls. Analysis jobs have a dedicated Bull queue with concurrency limit set below the Claude rate limit threshold. Failed jobs automatically retry up to 3 times before marking as failed. Rate limit errors are never stored as analysis results — they trigger a retry, not a failure state shown to the user.</div>
  </div>

  <h3 style="margin-bottom:12px;margin-top:24px;color:var(--amber)">Warnings — will degrade experience if not handled</h3>

  <div class="problem-block warn">
    <div class="problem-title"><span class="tag tag-amber" style="margin:0">Warning 7</span> Cookie consent banners blocking content</div>
    <div class="problem-body">Nearly every European app shows a cookie consent banner. The crawler screenshots the banner, not the actual page. All analysis is about the consent UI, not the product.</div>
    <div class="problem-solution">Before crawl begins, run a detection pass for common consent banner selectors (OneTrust, Cookiebot, etc.). Automatically click the accept button. If no known selector found, take a screenshot and ask Claude to identify and click the dismiss element before proceeding.</div>
  </div>

  <div class="problem-block warn">
    <div class="problem-title"><span class="tag tag-amber" style="margin:0">Warning 8</span> Crawler looping on infinite scroll or pagination</div>
    <div class="problem-body">An app with infinite scroll or paginated content looks like an endless source of new screens. The crawler scrolls forever or clicks Next page repeatedly, never finishing.</div>
    <div class="problem-solution">Visual fingerprinting catches repeated content — perceptual hash similarity above 90% triggers deduplication. Additionally cap maximum screenshots per domain path at 5. If same path is visited more than 5 times with different scroll positions, mark it as infinite scroll and only analyse the first viewport.</div>
  </div>

  <div class="problem-block warn">
    <div class="problem-title"><span class="tag tag-amber" style="margin:0">Warning 9</span> External links taking crawler off the target domain</div>
    <div class="problem-body">App links to documentation, social media, or partner sites. Crawler follows them and spends the entire run analysing someone else's website.</div>
    <div class="problem-solution">Intercept all navigation events. Compare the destination domain against the initial target domain. Any navigation leaving the target domain is blocked automatically. Log it as an "external link found" event in the report without following it.</div>
  </div>

  <div class="problem-block warn">
    <div class="problem-title"><span class="tag tag-amber" style="margin:0">Warning 10</span> Session cookie expiring mid-crawl</div>
    <div class="problem-body">Long scans on apps with short session timeouts. User gets logged out 3 minutes into a 10-minute crawl. Every subsequent screen is the login page. Entire analysis is useless.</div>
    <div class="problem-solution">Monitor each screenshot for login page indicators (login form present, URL matches auth route). If detected mid-crawl, automatically re-authenticate using stored credentials before continuing. If re-auth fails, pause the run and notify user via WebSocket event with option to update credentials.</div>
  </div>

  <div class="problem-block warn">
    <div class="problem-title"><span class="tag tag-amber" style="margin:0">Warning 11</span> File download dialogs blocking navigation</div>
    <div class="problem-body">User clicks a button that triggers a file download. Browser shows a download dialog. Playwright hangs waiting for navigation that never comes. Crawl freezes.</div>
    <div class="problem-solution">Intercept all download events before they trigger. Cancel them automatically. Log as "download trigger found on this screen" in the report. Never let a download block navigation.</div>
  </div>

  <div class="problem-block warn">
    <div class="problem-title"><span class="tag tag-amber" style="margin:0">Warning 12</span> Modal and overlay states not being captured</div>
    <div class="problem-body">Important screens exist inside modals — confirmation dialogs, form modals, image lightboxes. A basic crawler never triggers them. Analysis misses entire interaction patterns.</div>
    <div class="problem-solution">After landing on each screen, run a modal detection pass — look for buttons whose labels or ARIA roles suggest they open modals (confirm, delete, edit, view, details). Click each one, screenshot the result, close, continue. This is a separate pass from the main navigation, run after the primary crawl completes.</div>
  </div>

  <div class="problem-block warn">
    <div class="problem-title"><span class="tag tag-amber" style="margin:0">Warning 13</span> Video file too large to download</div>
    <div class="problem-body">A 10-minute crawl session at full resolution produces an MP4 that could be 200-400MB. Users on slow connections can't download it. Hosting costs are high.</div>
    <div class="problem-solution">Record at 1280x800 maximum resolution and compress with H.264 at CRF 28 via FFmpeg post-processing. Target under 50MB for a 10-minute session. Offer two quality options on download — web quality (compressed) and full quality — with file size shown on the button before downloading.</div>
  </div>

  <div class="problem-block warn">
    <div class="problem-title"><span class="tag tag-amber" style="margin:0">Warning 14</span> User closes tab mid-analysis</div>
    <div class="problem-body">Analysis runs are long. User closes the tab to do something else. When they come back the run is gone. All progress lost.</div>
    <div class="problem-solution">Jobs run on the server via Bull — completely independent of browser tab. When user returns and navigates to the run, it reconnects via WebSocket and replays all events since disconnection. Show run progress on the dashboard home page so users can always see active scans. Email notification when run completes (opt-in).</div>
  </div>

  <h3 style="margin-bottom:12px;margin-top:24px;color:var(--blue)">Info — edge cases worth handling early</h3>

  <div class="problem-block info">
    <div class="problem-title"><span class="tag tag-blue" style="margin:0">Info 15</span> Canvas and WebGL content</div>
    <div class="problem-body">Apps with canvas-based UIs (games, data visualisations, design tools) render content Claude can't analyse meaningfully from a screenshot.</div>
    <div class="problem-solution">Detect canvas elements occupying more than 30% of the viewport. Flag those screens with a note: "This screen contains canvas/WebGL content. Visual analysis may be limited." Still run UX/copy analysis on any non-canvas elements present.</div>
  </div>

  <div class="problem-block info">
    <div class="problem-title"><span class="tag tag-blue" style="margin:0">Info 16</span> Apps requiring MFA or 2FA</div>
    <div class="problem-body">Two-factor authentication requires a code from the user's phone. Can't be automated. Crawl fails at login.</div>
    <div class="problem-solution">During setup, detect if the app's login flow has a 2FA step after entering credentials. If detected, pause and prompt user: "This app uses 2FA. Enter a valid session token from your browser's cookies instead of credentials." Provide instructions for extracting session cookies from Chrome DevTools.</div>
  </div>

  <div class="problem-block info">
    <div class="problem-title"><span class="tag tag-blue" style="margin:0">Info 17</span> PDF generation timing out on large reports</div>
    <div class="problem-body">A scan with 50 screens and many annotated screenshots makes the PDF generation take too long. Request times out. User sees an error.</div>
    <div class="problem-solution">PDF generation is a separate Bull job, not a synchronous API call. User clicks Generate PDF — job is queued — WebSocket event fires when ready — download link appears. Never block the response waiting for PDF generation. Show "Generating PDF..." progress state.</div>
  </div>

  <div class="problem-block info">
    <div class="problem-title"><span class="tag tag-blue" style="margin:0">Info 18</span> Annotations misaligned on retina/HiDPI screens</div>
    <div class="problem-body">Playwright captures screenshots at device pixel ratio 1x. The accessibility tree returns coordinates at 1x. But the dashboard renders the video at a different size. Annotation boxes don't align with the elements they're pointing at.</div>
    <div class="problem-solution">Normalise all coordinates to the video display dimensions at annotation render time. Store raw coordinates from the accessibility tree, compute the scale factor between the original screenshot dimensions and the rendered video dimensions, apply scale to all annotation positions before drawing to canvas.</div>
  </div>

  <div class="problem-block info">
    <div class="problem-title"><span class="tag tag-blue" style="margin:0">Info 19</span> Claude false positives destroying trust</div>
    <div class="problem-body">Claude flags an intentional minimalist design as "empty state — needs more content." Developer dismisses the tool entirely after one wrong annotation. Precision matters more than coverage.</div>
    <div class="problem-solution">System prompt explicitly instructs Claude: "Only flag issues you would raise in a real design review meeting. If unsure whether something is intentional, do not flag it. Precision over recall. Include a confidence score on each finding — only return findings above 80% confidence." Build a thumbs up/down on each finding so users can mark false positives. Use feedback to iterate prompt quality.</div>
  </div>

  <div class="problem-block info">
    <div class="problem-title"><span class="tag tag-blue" style="margin:0">Info 20</span> Multiple browser tabs opened by target app</div>
    <div class="problem-body">Some apps open content in new tabs. Playwright by default only controls the original page. New tab content is never analysed.</div>
    <div class="problem-solution">Listen for new page events on the browser context. When a new tab opens, check if it's on the same domain. If yes, add it to the crawl queue. If no, close it. This catches in-app popups and same-domain tab opens without following external links.</div>
  </div>

  <div class="problem-block info">
    <div class="problem-title"><span class="tag tag-blue" style="margin:0">Info 21</span> App uses localhost or requires VPN</div>
    <div class="problem-body">Developer wants to test a staging environment on localhost:3000 or an app behind a VPN. The cloud-hosted crawler can't reach it.</div>
    <div class="problem-solution">V1 — document clearly in onboarding that the app must be publicly accessible. Provide a guide for exposing localhost via ngrok. V2 — offer a downloadable local crawler agent that runs on the user's machine and streams results to the cloud dashboard.</div>
  </div>

  <div class="problem-block info">
    <div class="problem-title"><span class="tag tag-blue" style="margin:0">Info 22</span> Playwright browser memory leak on long runs</div>
    <div class="problem-body">Playwright browser contexts accumulate memory over long crawl sessions. On 50+ screen apps the worker process runs out of memory and crashes mid-run.</div>
    <div class="problem-solution">Create a new browser context (not a new browser) every 20 pages. Transfer the session cookie to the new context. This resets the memory footprint without requiring re-authentication. Monitor memory usage per worker with a 500MB threshold — if exceeded, force a context reset before continuing.</div>
  </div>

  <div class="problem-block info">
    <div class="problem-title"><span class="tag tag-blue" style="margin:0">Info 23</span> Annotated video audio sync</div>
    <div class="problem-body">FFmpeg merging the canvas annotation overlay with the video can introduce audio/video sync issues if frame rates don't match perfectly.</div>
    <div class="problem-solution">Record video without audio (apps don't need audio for QA). This eliminates the sync problem entirely. The annotated video is silent. If audio is ever needed in future, use FFmpeg's -vsync cfr flag to enforce constant frame rate before merging.</div>
  </div>

  <div class="problem-block info">
    <div class="problem-title"><span class="tag tag-blue" style="margin:0">Info 24</span> Analysis results for a screen arriving after report is generated</div>
    <div class="problem-body">User ends the run manually while some analysis jobs are still queued. Report is generated. Then the remaining analysis results arrive. Report is now incomplete but the user already has it.</div>
    <div class="problem-solution">Reports are generated lazily — they pull from the database at request time, not at run completion time. The shareable link always serves the latest version of the analysis. Add a "last updated" timestamp to the report. If the user views the report while jobs are still queued, show a banner: "Analysis still running — some screens pending. This report will update automatically."</div>
  </div>
</div>
