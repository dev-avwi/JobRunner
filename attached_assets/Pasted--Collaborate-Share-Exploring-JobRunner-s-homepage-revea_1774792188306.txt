JobRunner — Full-Stack Technical Audit & Competitive Analysis
Prepared by: Manus AI
Date: March 29, 2026
Target Application: JobRunner — Job management platform for Australian trade businesses
Audit Scope: Architecture, Feature Completeness, Security, Scalability (1,000+ businesses), Testing, Production Readiness, and Competitive Comparison
﻿
Executive Summary
JobRunner is a genuinely impressive product. For an application still in beta, it has assembled a feature set that rivals platforms that have been in market for a decade. The AI Receptionist, native SWMS/WHS compliance tooling, and the depth of its job-to-payment workflow are legitimate competitive differentiators in the Australian tradie software market.
However, the technical foundation beneath those features carries serious risk. The application has been built with a "ship features fast" philosophy — which is correct for beta — but several critical issues must be resolved before the platform can safely scale to 1,000 businesses. The most urgent concerns are a 4.45MB monolithic JavaScript bundle with no code splitting, a complete absence of HTTP security headers including Content Security Policy, no rate limiting on authentication endpoints, and no production error monitoring. These are not minor polish items; they are the kind of issues that cause breaches, crashes, and churn at scale.
The honest verdict: JobRunner is a 5.4/10 today — not because the product is bad, but because the engineering foundation needs to catch up with the product vision. The good news is that every issue identified in this report is fixable, and most of the critical ones can be addressed in a focused two-to-four week sprint.

The confirmed technology stack is modern and well-chosen for a fast-moving startup. The frontend is built with React, bundled via Vite, and uses Wouter for client-side routing. The backend is Node.js with Express.js, connecting to a PostgreSQL database via the Drizzle ORM. The application is hosted on Google Cloud infrastructure (confirmed via server: Google Frontend and via: 1.1 google response headers). Real-time features use a combination of WebSocket connections, Server-Sent Events, and client-side polling.

Critical Architecture Problem: The Monolithic Bundle
The most damaging architectural decision in the current build is the delivery of the entire application as a single, uncompressed JavaScript file of 4.45 megabytes. There is no code splitting, no lazy loading, and no route-based chunking. Every user — whether a field worker checking their schedule on a phone or an office manager reviewing reports — downloads the complete application, including administrative dashboards, AI visualization tools, WHS compliance forms, and all third-party library code, before they can interact with a single feature.
At a 4G connection speed of approximately 20 Mbps, this bundle takes roughly 1.8 seconds to download alone, before parsing and execution. On a typical Australian 3G mobile connection (around 3 Mbps), this extends to over 12 seconds. For tradespeople working in areas with poor signal — which is the majority of JobRunner's target market — this is a critical user experience failure. Vite has excellent built-in support for dynamic imports and route-based code splitting; the fix is a configuration change, not a rewrite.
State Management Patterns
The application makes 422 calls to invalidateQueries throughout the codebase. While TanStack Query's cache invalidation is the correct mechanism for keeping data fresh after mutations, this volume suggests a pattern of over-invalidation. When a user updates a job status, for example, it is likely that the jobs list, the dashboard KPIs, the calendar view, the client history, and the activity feed are all being invalidated simultaneously, triggering up to five or more parallel API requests to the server. At scale with concurrent users, this multiplier effect creates unnecessary database load. The solution is targeted, surgical cache invalidation using specific query keys rather than broad invalidation patterns.
Real-Time Architecture
The application relies on refetchInterval polling in 31 separate instances to simulate real-time updates. Only 3 WebSocket connections and 2 SSE instances were identified. Polling is the simplest real-time mechanism to implement, but it is the least efficient at scale. With 1,000 businesses and an average of 5 active users each, 5,000 clients polling every 5–30 seconds generates between 10,000 and 60,000 background HTTP requests per minute purely for status checks — before any actual user actions. This architecture will saturate the Express server and the database connection pool long before reaching the 1,000-business target.
Code Organization
The routing structure is well-organized and demonstrates clear separation of concerns between public pages, authenticated app routes, admin routes, and portal routes. The presence of dedicated endpoints for every feature domain (WHS, SWMS, dispatch, AI, billing, etc.) indicates a reasonably modular backend structure. However, the inclusion of a Replit development banner script in the production index.html is a significant red flag. This script (https://replit.com/public/js/replit-dev-banner.js ) is a third-party resource that should never appear in production, and its presence indicates that the deployment pipeline does not include a proper build sanitization step.

3. Security Audit
Critical Vulnerabilities
Missing Rate Limiting on Authentication Endpoints. Fifteen rapid sequential login attempts to /api/auth/login with invalid credentials all returned standard 401 Unauthorized responses. No 429 Too Many Requests response was triggered, and no rate-limit headers (X-RateLimit-*, Retry-After) were present. This means an attacker can attempt unlimited password combinations against any known email address without restriction. With a user base of 1,000 businesses, credential stuffing attacks become a serious risk. The fix is to implement express-rate-limit with a Redis store on all authentication endpoints, limiting to 5-10 attempts per IP per 15-minute window.
Absent HTTP Security Headers. The application returns no Content Security Policy, no X-Frame-Options, no X-Content-Type-Options, and no Referrer-Policy header on any response. The absence of CSP is particularly concerning because it means any successful XSS injection can execute arbitrary scripts without restriction. The absence of X-Frame-Options leaves the application vulnerable to clickjacking attacks. Helmet.js is already a dependency in most Express applications; enabling it with a strict configuration would resolve all of these issues in a single change.
Medium-Severity Issues
Session Cookie Security. The primary session cookie (GAESA) is set without HttpOnly, Secure, or SameSite flags. Without HttpOnly, any successful XSS attack can exfiltrate the session token. Without SameSite=Strict, the session is vulnerable to cross-site request forgery. These flags must be enforced in the Express session configuration.
Information Disclosure via Public Endpoints. The /api/auth/config endpoint is publicly accessible and reveals the internal development domain tradietrack.replit.app in the Apple OAuth redirect URI configuration. This confirms the application's development history and provides an attacker with a secondary target. The /api/beta/status endpoint reveals that the platform has 24 business signups, which is competitive intelligence that should not be publicly accessible.
Apple OAuth Misconfiguration. The Apple OAuth redirect URI is configured as a comma-separated string ("https://tradietrack.replit.app,jobrunner.com.au,jobrunner.org/api/auth/apple/callback" ), which is almost certainly a bug. OAuth redirect URIs must be individual, exact-match strings. This configuration likely means Apple Sign-In is non-functional.
Technology Fingerprinting. The x-powered-by: Express header is present on all responses, advertising the backend framework to potential attackers. This should be disabled with app.disable('x-powered-by').
Positive Security Findings
The application correctly enforces HTTPS via HSTS with a 63,072,000-second max-age (approximately 2 years) including subdomains, which is excellent. All tested sensitive API endpoints correctly return {"error":"Authentication required"} when accessed without a valid session, indicating that the authentication middleware is consistently applied. No API keys, secrets, or sensitive credentials were found in the frontend JavaScript bundle. The application uses Zod and Yup for input validation, providing a meaningful defense against malformed input.

4. Scalability Assessment for 1,000+ Businesses
The Polling Problem
The most immediate scalability threat is the reliance on client-side polling for real-time updates. At 1,000 businesses with an average of 5 concurrent users per business, 5,000 clients each polling every 10 seconds generates 30,000 HTTP requests per minute to the Express server — purely for background data refresh, before any user-initiated actions. Each of these requests hits the Express process, creates a database connection, executes one or more SQL queries, and returns a response. This is an unsustainable architecture that will cause server saturation well before 500 businesses. The solution is to replace polling with a proper WebSocket server (Socket.io or native WebSocket) or a managed real-time service, broadcasting targeted updates to subscribed clients only when data changes.
Database Considerations
PostgreSQL is an excellent database choice and can handle the load of 1,000 businesses with proper configuration. However, the aggressive invalidateQueries pattern means the database is queried far more than necessary. Each user action likely triggers 3-8 follow-up SELECT queries from the client. At 1,000 businesses with 5 users each, a single common action (like updating a job status) could generate 25,000 database reads within seconds if all users happen to trigger it simultaneously. Proper database indexing on business_id, user_id, job_id, and created_at columns is essential, as is implementing a read replica for reporting queries.
Session Storage
If the Express application uses the default in-memory session store (which is common in development), it will be incompatible with horizontal scaling. Running multiple Express instances behind a load balancer requires a shared session store. Redis is the standard solution and should be implemented before any horizontal scaling is attempted.
Background Job Processing
Heavy operations including PDF generation, bulk SMS dispatch, Xero synchronization, AI processing, and email delivery appear to be handled synchronously within the Express request-response cycle. At scale, these operations will cause API timeouts and degrade the user experience for all concurrent users. A dedicated background job queue using BullMQ with Redis is essential. This decouples long-running tasks from the HTTP layer, allowing the API to respond immediately while work is processed asynchronously.
File Storage and Media
The application supports photo uploads, receipt scanning, and document generation. At 1,000 businesses with active field workers uploading job photos, the storage and delivery requirements become significant. There is no evidence of a CDN-backed object storage solution (such as AWS S3 with CloudFront or Google Cloud Storage with Cloud CDN) for user-uploaded media. Storing files on the application server filesystem is not viable at scale.

5. Testing Coverage
No testing frameworks (Vitest, Jest, Cypress, Playwright) were detected in the production artifacts. The it( and test( patterns found in the JavaScript bundle are from third-party library code, not application-level tests. There is no evidence of a CI/CD pipeline that enforces test coverage before deployment.
The critical paths that are most likely untested — and most dangerous if they fail — are the Stripe webhook handler (which processes payment confirmations), the Twilio SMS webhook (which handles inbound messages), and the Vapi.ai call routing logic. If any of these fail silently, businesses lose revenue and clients receive no response.
Recommended Testing Strategy:
The recommended approach is a three-tier testing pyramid. Unit tests using Vitest should cover all utility functions, Zod schema validations, and pure business logic functions. Integration tests using Supertest should cover every API endpoint, with particular focus on authentication flows, RBAC permission checks, and third-party webhook handlers (using mocked Stripe and Twilio payloads). End-to-end tests using Playwright should cover the five most critical user journeys: account registration and onboarding, job creation and assignment, quote creation and client approval, invoice generation and Stripe payment, and team member invitation and role assignment.

6. Production Readiness
Error Monitoring and Observability
The application has no integrated error tracking service. No Sentry, Datadog, LogRocket, or equivalent service was detected in the frontend bundle or API responses. This means that when a user experiences a crash, an unhandled promise rejection, or an API error in the field, the development team has no automated visibility into it. The 73 console.error calls found in the bundle suggest errors are being caught and logged to the browser console, but never surfaced to the team. Integrating Sentry takes approximately two hours and provides immediate, actionable crash reports.
Deployment Pipeline
The presence of the Replit development banner script (https://replit.com/public/js/replit-dev-banner.js ) in the production index.html is the clearest indicator of an immature deployment pipeline. A production build process should strip all development-only scripts, environment-specific configurations, and debug tooling. This script loads a third-party JavaScript file from Replit's servers on every page load in production, which is both a performance overhead and a security risk (third-party script injection).
Health Monitoring
The /api/health endpoint returns a well-structured JSON response including database connectivity status and response time in milliseconds. This is excellent practice and provides a solid foundation for uptime monitoring. The Service Worker provides graceful offline fallback pages rather than browser-native error screens, which is a positive user experience decision.
Graceful Shutdown
There is no publicly verifiable evidence of graceful shutdown handling (SIGTERM/SIGINT handlers, connection draining) in the Express application. This is important for zero-downtime deployments on Google Cloud, where instances are replaced during updates.

Competitive Positioning Summary
Against ServiceTitan: JobRunner is not trying to compete with ServiceTitan in the enterprise segment, and it should not. ServiceTitan requires $5,000–$50,000 in implementation fees and $245+ per technician per month. It is built for businesses with 20+ technicians and dedicated operations managers. JobRunner's sweet spot is the 1–15 person trade business that wants enterprise-grade features at SMB pricing. In that segment, JobRunner wins on price, simplicity, and innovation (AI Receptionist, AI quote generation) while ServiceTitan wins on depth of reporting, marketing automation, and enterprise integrations.
Against Tradify: This is JobRunner's most direct competitor. Tradify has 9,000+ reviews and years of market trust. However, JobRunner's feature set is substantially broader — Tradify charges extra for SMS, gates AI features behind its highest tier, and lacks inventory management, purchase orders, and a built-in AI receptionist. If JobRunner can close the gap on stability and mobile app maturity, it has a credible path to taking market share from Tradify in the 1–10 person business segment.
Against ServiceM8: ServiceM8's job-based pricing model is clever and scales well for businesses with variable job volumes. Its iOS app is arguably the best in the market for Apple device users, with deep hardware integration (offline sync, Siri shortcuts, Apple CarPlay). JobRunner wins on Android parity, AI features, and pricing transparency. ServiceM8 wins on iOS depth, offline reliability, and its mature third-party add-on ecosystem.
Against AroFlo: AroFlo targets a different customer entirely — mid-market to enterprise businesses with complex project management needs, large inventory requirements, and multi-site operations. Its $365/month minimum and $2,900 implementation fee make it inaccessible to the small tradie. JobRunner is not competing with AroFlo for the same customer. However, as JobRunner matures and adds Gantt-chart project management and deeper inventory controls, it could begin to compete for AroFlo's smaller customers.

Immediate (This Week):
The first priority is to remove the Replit development banner script from index.html. This is a one-line change that eliminates a third-party script injection risk and removes a public indicator of the application's development history. Simultaneously, enable Helmet.js in the Express backend with a strict configuration to immediately add CSP, X-Frame-Options, X-Content-Type-Options, and Referrer-Policy headers. Add express-rate-limit with a Redis store to the authentication endpoints. These three changes resolve the most critical security vulnerabilities in under a day of engineering work.
Short-Term (Next Two Weeks):
Implement Vite's dynamic import code splitting to break the 4.45MB bundle into route-based chunks. The admin dashboard, WHS module, AI visualization tools, and reporting suite should each be lazy-loaded. This will reduce the initial bundle to under 500KB for most users and dramatically improve mobile load times. Simultaneously, integrate Sentry for both frontend and backend error tracking to gain immediate visibility into production issues.
Medium-Term (Next Month):
Replace the 31 refetchInterval polling instances with a WebSocket broadcast architecture. This is the single most impactful change for scalability. Implement a Redis session store to enable horizontal scaling. Establish a BullMQ worker queue for PDF generation, SMS dispatch, and AI processing. Add QuickBooks integration to close the gap with competitors.
Long-Term (Next Quarter):
Establish a comprehensive automated testing suite covering unit tests, API integration tests, and end-to-end Playwright tests for critical user journeys. Implement a proper CI/CD pipeline with mandatory test coverage gates before deployment. Migrate user-uploaded media to a CDN-backed object storage solution. Consider adding Zapier/n8n integration to unlock a marketplace of workflow automations.

Conclusion
JobRunner is one of the most ambitious and feature-complete new entrants in the Australian trade business software market. The product vision is clear, the UX is clean and modern, and the inclusion of AI-native features like the Vapi.ai receptionist and AI quote generation puts it genuinely ahead of incumbents in terms of innovation. The pricing model is well-calibrated for the Australian SMB market.
The challenge is that the engineering foundation needs to mature rapidly to support the product ambitions. The security vulnerabilities, performance bottlenecks, and scalability limitations identified in this report are not insurmountable — they are the expected growing pains of a fast-moving startup that has prioritized feature delivery over technical hardening. The path forward is clear: harden the security posture, split the bundle, replace polling with WebSockets, add observability, and build a testing culture. Execute those priorities, and JobRunner has a genuine shot at becoming the dominant platform for Australian trade businesses in the 1–20 employee segment.
